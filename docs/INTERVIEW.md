## 二、核心问题自问自答(按面试出现频率排序)

### Q1. 你的项目怎么防止超卖？（必考）

**答（按分层讲，体现体系化思维）：**

1. **Redis 层**：库存预热到 Redis，用 Lua 脚本把"查库存+减库存"合成一个原子操作，单线程执行的 Redis 保证不会扣成负数
2. **数据库层**：即使 Redis 出问题，DB 还有 `UPDATE ... SET stock = stock - 1 WHERE stock > 0`，UPDATE 自带行锁，条件由数据库原子判断
3. **兜底**：`seckill_order` 表 `(user_id, goods_id)` 唯一索引，重复下单触发 DuplicateKeyException，事务回滚

**追问：为什么不直接用数据库扣库存？**
> 数据库行锁在高并发下会成为瓶颈，所有请求排队抢同一行的锁，QPS 会被压得很低。Redis 是内存操作，单机就能扛 10 万 QPS，把流量挡在 DB 之前。

**追问：Redis 扣了库存但建单失败怎么办？**
> 我做了补偿机制 `compensateRedis`：建单失败时把 Redis 库存加回去、删掉订单占位 Key、摘掉售罄标记。保证最终一致。

### Q2. 为什么用 RabbitMQ？（必考）

**答：**
1. **削峰填谷**：秒杀瞬间 QPS 可能上万，但数据库每秒只能处理几百次写。接口只扣 Redis 库存然后发 MQ 立即返回，消费者按自己的节奏（prefetch=1）慢慢建单，数据库压力始终平稳
2. **异步化**：用户不需要等建单完成，接口毫秒级返回"排队中"，体验更好
3. **解耦**：下单和库存逻辑分开，以后加"发优惠券"、"发短信通知"只需要加个消费者，不改主流程

**追问：为什么不用 Kafka？**
> Kafka 是为大数据日志场景设计的，吞吐极高但单条延迟相对高，且没有内置的延迟队列。秒杀下单量没到 Kafka 的场景，而 RabbitMQ 的路由、确认机制、延迟队列(TTL+死信)更贴合业务系统。

**追问：消息丢了怎么办？**
> 我做了手动 ACK：业务成功才 ack，系统异常 nack 让消息重回队列。生产环境还可以加 confirm 机制确认消息到达交换机，再加本地消息表做最终兜底。

**追问：消息重复消费了怎么办？（幂等）**
> 数据库 `(user_id, goods_id)` 唯一索引兜底，重复消费只会触发 DuplicateKeyException，不会重复建单。

### Q3. Redis 缓存穿透/击穿/雪崩怎么防？（必考）

**答（结合自己代码讲）：**
- **穿透**（查不存在的 key）：我在商品详情里做了"缓存空值"——商品不存在时把空标记缓存 60 秒，恶意刷不存在的 ID 打不到数据库。更严谨的方案是布隆过滤器
- **击穿**（热点 key 过期瞬间被打崩）：秒杀商品详情几乎不变，用长 TTL + 管理端变更时主动失效缓存（`evictGoodsCache`）。也可以用互斥锁/逻辑过期
- **雪崩**（大量 key 同时过期）：TTL 加了随机值（1 小时 + 0~10 分钟随机），避免同一时刻大批失效

### Q4. 分布式锁为什么用 Redisson？（高频）

**答：**
1. **看门狗自动续期**：默认 30 秒锁，后台线程每 10 秒检查，业务没执行完就自动续期。自己写 setnx 很容易出现"锁过期了但业务没做完"的经典坑
2. **可重入**：同一线程可以重复拿锁，不用担心死锁
3. **tryLock 等待机制**：可以设置"等多久、锁多久"，比 setnx 手动重试优雅

**追问：Redisson 锁的缺点？**
> 在 Redis 主从架构下，如果主节点挂了但锁还没同步到从节点，新主会丢锁。强一致场景要用 RedLock 或 Zookeeper，但秒杀这种"宁可拒绝也不能超卖"的场景，Redisson 单机/哨兵已经够用。

### Q5. 限流怎么做的？（高频）

**答：**
用了 Redisson 的 `RRateLimiter`，基于 Redis 的令牌桶，配合自定义注解 `@RateLimit(count=5, period=1)` + AOP 切面实现"单用户每秒最多 5 次"。

**追问：为什么不用 Guava RateLimiter？**
> Guava 是单机限流，每个 JVM 实例各发各的令牌。如果部署 3 台机器，实际限流阈值就变成了 3 倍。Redisson 把令牌桶放在 Redis 里，所有实例共享一份，是分布式限流。

### Q6. JWT 登录是怎么做的？（基础但必问）

**答：**
登录成功后签发 JWT（HS256 签名，载荷放用户 ID），拦截器统一解析 `Authorization: Bearer <token>`，校验通过后把用户存进 ThreadLocal（`UserContext`），请求结束时 `remove()` 防止线程复用导致的数据污染。

**追问：JWT 怎么退出登录/续期？**
> 无状态 JWT 本身不能主动失效，可以加 Redis 黑名单或缩短有效期 + Refresh Token。我项目里是 7 天有效期，面试可以主动提这个局限性。

### Q7. 压测怎么做的？QPS 多少？（展示真实性）

**答：**
写了一个 JUnit 压测类：预置 200 个用户，用 `CountDownLatch` 让 200 个线程同一时刻起跑，每个用户发 1 次秒杀请求。
实测：975ms 跑完，端到端 QPS 约 205，100 人抢到、100 人售罄，**DB 剩余库存 0、订单数 100，零超卖零差错**。
瓶颈分析：当前是单线程消费者（prefetch=1）串行落库，如果要更高吞吐可以加多消费者或批量入库。

**追问：怎么继续提升 QPS？**
> 1. MQ 消费端加并发（concurrency 参数）或批量建单
> 2. Tomcat 线程池调大
> 3. Redis 连接池调优
> 4. 上集群，Nginx 负载均衡多台应用

### Q8. 秒杀系统还缺什么？（考察广度，主动说更好）

- **延迟关单**：用户抢到不付款占库存 → RabbitMQ TTL + 死信队列，30 分钟未支付自动取消订单回滚库存
- **防黄牛**：秒杀地址动态化（活动开始才发签名 URL）、验证码、IP 黑名单
- **库存扣减分层**：更极致的方案是把库存拆到 Redis Cluster 多 key 分片，防止单 key 热点
- **监控告警**：Prometheus + Grafana 监控接口 QPS、Redis 命中率、MQ 堆积量
